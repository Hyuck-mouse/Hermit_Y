# 竞争条件漏洞（Race Condition）

## 描述
服务端对"一次性"操作（扣款、领券、签到、投票、提现）缺乏原子性或并发控制，多个请求同时到达时校验环节（如余额是否够、是否已领）依次通过，但实际写入前都放行，导致同一操作被重复执行。属业务逻辑漏洞，危害直接表现为资产损失。

## 典型场景
- **余额双花**：余额 100，并发发 10 个转账 100 的请求，多个都通过"余额≥100"校验，账户被扣成负数或只扣一次。
- **优惠券重复使用**：同一张券并发核销多次，多个请求都看到"未使用"。
- **签到刷次数**：每日签到并发多次，绕过"今日已签"判断。
- **投票刷票**：并发投同一选项，绕过"每人一票"限制。
- **抽奖/抢红包**：并发领取，库存超扣或多中。
- **提现/兑现**：并发提现超出余额。

## 触发条件
- 服务端采用"先查后改"非原子流程：`SELECT 余额 → 判断 → UPDATE`。
- 无数据库行锁、无唯一索引、无分布式锁、无幂等 token。
- 限速/幂等只在单请求维度，未覆盖并发窗口。

## 检测方法（快速验证）
1. **抓关键请求**：找到"扣减/领取/投票"接口，确认是单次 POST。
2. **重放两次**：先用正常重放看第二次是否被拒（确认有校验）。
3. **并发重放**：用同一会话/同一参数同时发 10~50 个请求，看是否多个成功。
4. **前后对比**：测试前后查余额/券状态/票数，差值 ≠ 成功请求数即存在竞态（如发了 20 个、扣了 1 次但券被核销 20 次）。

## 并发利用要点
- **同一会话**：用同一 `session_id` 发所有请求，共享 Cookie/Token（多数签到/领券要求登录态）。
- **同时触达**：延迟设 0，让所有请求尽可能同时到达服务端校验窗口。
- **阶梯延迟**：若服务端有微秒级时间戳防重，可设 `delay_ms` 错峰（如 `delay_ms=5`）逐个击破。
- **预热连接**：高并发前先发一个请求建立 TCP/TLS 连接，减少握手时间差。

## 使用 logic_race_condition 工具测试

工具签名：`logic_race_condition(url, method="POST", data="", json_data="", headers="", concurrency=10, delay_ms=0, session_id="")`

### 标准测试流程
1. **登录拿会话**：`logic_session_http` 登录，记下 `session_id`（如 `"attacker"`），保证并发请求都带登录态。
2. **准备请求体**：
   - `data`：表单 JSON 串，如 `'{"coupon_id":"C123","order_id":"O456"}'`。
   - `json_data`：JSON 体 JSON 串（与 `data` 二选一）。
   - `headers`：额外头（如 `{"X-CSRF-Token":"xxx"}`）。
3. **设置并发**：
   - `concurrency`：并发数，工具内部上限 50，默认 10。先 10，再 30、50 递增。
   - `delay_ms`：0 = 同时发送；>0 时第 i 个请求会等待 `delay_ms*i/1000` 秒，做阶梯触发。
4. **执行并解读**：
   - `success_count`：状态码 200 的请求数。>1 即高度可疑（本应只成功 1 次）。
   - `status_distribution`：状态码分布，如 `{200:5, 400:5}` 说明一半绕过校验。
   - `findings`：自动判定——所有成功响应内容相同 → "操作被重复执行"；成功但内容不同 → "可能存在竞态"。
   - `error_count`：失败数（可能触发限速或异常）。
5. **核对业务后果**：测完查账户余额/券状态/签到记录/票数，与 `success_count` 比对，确认实际重复执行的次数。

### 示例（优惠券重复核销）
```
# 1. 登录
logic_session_http(session_id="attacker", method="POST", url="http://target/login",
                   json_data='{"username":"a","password":"a"}')

# 2. 并发核销同一张券
logic_race_condition(
    url="http://target/api/coupon/use",
    method="POST",
    json_data='{"coupon_id":"C123"}',
    concurrency=20,
    delay_ms=0,
    session_id="attacker"
)
# 若 success_count>1，且券被核销多次 → 竞态成立
```

### 示例（签到刷次数，阶梯延迟）
```
logic_race_condition(
    url="http://target/api/sign",
    method="POST",
    concurrency=15,
    delay_ms=10,
    session_id="attacker"
)
```

## 绕过技巧
- **限速绕过**：分批并发（每批 10、间隔 1s），或多账号并发各发 1 次。
- **多会话并发**：同一账号开多个 `session_id`（每次重新登录）绕过单会话限速；注意服务端可能按用户限速。
- **CSRF/幂等 token**：若 token 一次性，先 `logic_session_http` 拿一个新 token，构造后立即并发（token 在并发窗口内仍有效）。
- **预扣库存型**：先发一个"预占"再并发"确认"，两阶段流程分开测。
- **数据库锁绕过**：在"查询"和"扣减"之间插入慢请求（如带 `SLEEP` 的注入点）拉大窗口。

## 注意
- 余额/提现类竞态会造成真实资产损失，测试前确认授权与额度，优先用小额（1 分）。
- 工具单次最多 50 并发；更高并发可分批调用，注意别打挂目标。
- `success_count>1` 不等于业务上一定重复执行，必须核对最终状态（如实际扣了几次）。
- 测完 `logic_session_close` 释放会话。
